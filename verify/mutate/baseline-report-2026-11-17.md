## 第二批：release 闸门 8 条

发布项的判定链是 `版本 && CHANGELOG 本节 && 清单一致 && tag 之后没有未走闸的提交`。
夹具仓库（`package.json` 1.2.3 + `CHANGELOG.md` 的 `## v1.2.3` 节 + `tag v1.2.3`）逐项破坏一次：

| `:201` | `and->or` | **CHANGELOG 缺本节也报绿**（最危险的一条） |

夹具仓库必须 `git commit --no-verify`：本机全局装了 `core.hooksPath`，否则夹具提交会去跑本仓库的 p1。
第一版测试就是因为没加这个参数，`git tag` 建在了一个不存在的提交上，三条断言假红。

## 证明为等价的 4 条（不是"没测到"，是"改了没区别"）

`:205`（`head`）与 `:206`（`behind`）只服务于同一行文案：

```js
const behind = tagCommit && head && tagCommit !== head ? Number(sh(["rev-list","--count", …])) : 0;
if (after.total) bits.push(… "个提交，未走闸" …);
else if (behind) bits.push("tag 之后还有 …");
```

`after.total`（`git log`）与 `behind`（`git rev-list --count`）数的是同一区间：**只要 behind > 0，
after.total 就必然 > 0**，于是永远走前一支，`behind` 那一行永远不输出。四种变异都只改这个不可达数与那句死文案，
页面上逐字相同。已登记进 `verify/mutate/ignore.json`（附论证），而不是算作"存活"。

不删代码的原因：删了会让刚发布的这份基线行号全部失配；等下次结构性改动一并清掉。
