# 架构体检：看门的人自己有没有锁门

SignOff 给别人的仓库判覆盖、判口径、判账本，却没有一条检查它自己。

`tools/arch-health.mjs` 补这一条。判定只有四条，都能被反驳、都能被复现：

| 规则 | 内容 | 为什么 |
| --- | --- | --- |
| R1 | `lib/` 内部依赖图无环 | 成环意味着两个模块谁也离不开谁，改一个得同时理解两个 |
| R2 | `lib/core.js` 不 require 其它 lib 模块 | 基座一旦反向依赖，所有模块都被拖进同一团 |
| R3 | `lib/`、`gates/` 不 require `bin/` | 向上依赖入口 = 库不能单独使用 |
| R4 | 超过 1200 行的文件必须登记在基线台账 | 允许长，不允许"悄悄长" |

## 判定口径

- **存量债务登记在册，登记不等于通过。** `docs/arch-health-baseline.json` 记下当前超限文件与已有违规；
  工具只对"基线之外的新增"判红，退出码 1。
- **改阈值要写进提交说明。** `OVERSIZE_LIMIT` 就在脚本顶部，谁改谁解释。
- **评分只当体检表，不当 KPI。** 口径会随项目变；把它当目标，就会开始有人拆函数不拆职责。

拆分方向写在提交说明里，不在本文承诺时间。

## 使用

```bash
node tools/arch-health.mjs                # 人读：文件数、超限清单、新增违规
node tools/arch-health.mjs --json         # 机器读：给 CI / agent
node tools/arch-health.mjs --write-baseline   # 登记当前状态，并追加一条历史快照
```

CI 里作为独立步骤运行；失败只指向"新增违规"，不会因为历史债务把每次提交都判红。

## 和 Liri 的六层门禁差在哪

Liri 那套（`entry > ui > app > service > infra > core`）是为一个 98 万行、71 个子系统的仓库设计的。
SignOff 只有 8,744 行、26 个文件，照搬六层只会得到一张"几乎所有文件都在同一层"的空表。

这里取的是它的**原则**（分层必须可判定、超限必须登记、门禁而不是建议），不是它的**形状**。
哪天 `lib/` 真长出多个子系统，再加层；在那之前，四条规则已经能挡住"悄悄变烂"。
