# Boards: one core, several thin shells

The verdict is computed once, in `lib/`: `signoff report --json` and the MCP tool `signoff_report` are the only
readers of the evidence, and every board renders that output. A new surface therefore cannot grow a second
verdict, and a panel can never say "ready" while the page says "blocked".

## Surface matrix

| Platform / agent | Entry point | Data comes from | Prerequisite |
| --- | --- | --- | --- |
| DSH (this machine) | sidebar navigation row 4, "SignOff 看板"; the page fetches `/signoff-board/state` | `~/.signoff/reports/index.json` and `<repo>/report.json` | one `--mount` run in the repo |
| MCP clients (Claude Desktop, Cursor, Codex, …) | call `signoff_report` | the same CLI | register `signoff mcp` in the client |
| Terminal / scripts | `signoff report --json` | `.signoff/*.json`, `.signoff/audit.log`, git | none |
| Browser / archive / sharing | `signoff report --html --mount`; the page is a single file | the same | a browser |
| CI | the same command, then upload `~/.signoff/reports` as an artifact | the same | the npm package on the runner |
| Editor | tasks generated by `signoff init --editor` | the same CLI | none |

## Three things every new surface does

1. **Get the data**: prefer the MCP tool `signoff_report`; without MCP, spawn `signoff report --json`.
2. **Render the verdict by exit code** (0 pass / 1 has red / 2 usage or environment), and never paint "red" as a warning.
3. **Stay read-only**: no control that runs, skips, or relaxes a gate; running gates is an explicit `signoff run`.

## Why it is cut this way

There is one set of verdicts, so the page, the panel, and MCP cannot disagree. This is the delivery side of
`docs/REPORT-CONTRACT.md`: the contract governs the content (C1 read-only, C5 derivable verdict, C9 same rules
across repositories), this file governs where that content is shown.
