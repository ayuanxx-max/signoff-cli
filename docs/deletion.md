# 删除流程：删除也要证据

一次真实事故的教训（不是 SignOff 自己的，是同类项目的）：把"看起来没人引用"的子系统当死代码删掉，
第二天整批回滚。删代码比写代码更容易造成不可逆损失，因为它删的是别人正在依赖的东西。

## 四条规则

| # | 规则 | 判定方式 |
| --- | --- | --- |
| D1 | 删任何文件前，先写出"谁在用它"的证据 | 提交说明里贴 `grep`/引用计数结果，或 issue 链接 |
| D2 | 被删文件若在 `gates/`、`lib/`、`integrations/` 下，必须同步更新 README / docs 的引用 | `signoff p5` 会扫文档里的无数字断言，但扫不到断链；靠 D1 的证据清单人工核对 |
| D3 | 一次提交只删一件事；跨目录批量删要拆开 | 提交粒度，review 时可判 |
| D4 | 删完必须跑 `npm test` 与 `node tools/arch-health.mjs` | 两条命令都给出退出码 |

## 为什么不做成自动闸门

自动判"文件是否还有人用"需要跨仓库的引用图；SignOff 只看得到当前工作区，
做成闸门就会变成"猜"，猜错的方向恰好是不可逆的那一边。

所以这条是**流程 + 证据要求**，不是脚本。宁可慢一次，也不要删错一次。

## 反例

- 反例 1：`git rm` 之后靠 `git revert` 兜底。回滚能救代码，救不了"基于删除后状态写的新代码"。
- 反例 2：因为测试没覆盖就认定没人用。测试覆盖率低恰恰说明引用可能在别处。
- 反例 3：把"删除"和"重构"塞进同一个提交。出问题时无法只回滚其中一半。
