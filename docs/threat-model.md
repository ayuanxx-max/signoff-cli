# 威胁模型：SignOff 拿的是你的仓库权限

`docs/trust.md` 回答"这个提交当时真的过了吗"。这一篇回答另一个问题：
**一个判定工具凭什么值得你让它装钩子。**

## 它站在什么位置

SignOff 被请进一个仓库后，能做的事接近"仓库的 CI，但跑在你的机器上、以你的身份"：

| 它能 | 因为 |
| --- | --- |
| 读你的工作区 | 要算暂存树、扫密钥、读场景文件 |
| 以你的身份执行命令 | P1 要跑测试套件，P3 要跑收集脚本 |
| 写 `.signoff/` | marker、账本、检查点 |
| 装/改 git 钩子 | `install`、`ensure`、机器层 `core.hooksPath` |
| 拦住一次提交 | 非零退出码即判决 |

所以它的信任边界不是"一个 CLI"，而是"一段会在我提交时自动执行的代码"。

## 资产

1. 仓库内容与暂存树（读）
2. 你的凭据（`.signoff/secrets.json`、环境变量里的 token）
3. 证据链本身（账本、检查点、锚点）——被伪造就等于判决失效
4. 你的 shell（P1/P3 执行外部命令）

## 入口与攻击面

| 入口 | 攻击面 | 当前判定 |
| --- | --- | --- |
| `signoff.json`（仓库声明） | 恶意配置让检查变宽松、把命令换成别的 | 部分缓解：三条红线不随配置放开；配置本身不校验来源 |
| P1 的测试命令 | 命令来自仓库配置，等于"克隆即执行" | 未缓解（与 CI 同性质）：只在你信任的仓库里开钩子。落点是 `lib/p1.js` 的 `spawnSync(cmd, { shell: true })`——命令字符串必然过 shell |
| git 钩子 | 钩子被替换、`core.hooksPath` 被改 | 有自检：`signoff doctor` 报安装点与钩子状态 |
| `.signoff/audit.log` | 改内容、删末尾、换 key 重签 | 已缓解：内容哈希 + 链式 prev + 检查点 Merkle 根 + 可外发锚点（见 `trust.md`） |
| trailer / marker | 用别的树的 marker 冒充 | 已缓解：签名覆盖完整 40 位 tree；陈旧 marker 不写进提交信息 |
| `--no-verify` / `SIGNOFF_SKIP=1` | 绕过 | 不停用，但必须留痕：`audit` 会判 `skipped` |
| 密钥扫描 | 误报导致"反正都红"的疲劳 | 部分缓解：只在 guard 内跑、有白名单 |

## 七种攻击与现状

| # | 攻击 | 期望结果 | 证据位置 |
| --- | --- | --- | --- |
| A1 | 改提交信息里的 `Signoff-Pass` | `bad-signature` | `test/selftest.js` 的 trailers 段、签名校验段 |
| A2 | 改账本某条记录内容 | `content hash mismatch` | `p4 verify` 用例 |
| A3 | 删掉账本末尾 N 条 | `records were removed` | `p4 verify --checkpoint` 用例 |
| A4 | 换 key 重新签 | 只算 `self-signed`，除非 key 在 `allowed_signers` | 签名信任段 |
| A5 | 用陈旧 marker 冒充本次提交 | 不写入 trailer | "stale marker" 用例 |
| A6 | `--no-verify` 静默跳过 | 提交能成，但 `audit` 报 `skipped` | 跳过审计用例 |
| A7 | 把检查点锚点贴到别处对不上 | 锚点不匹配 | `--anchor` 用例 |

这七条要求"失败必须失败"，不是"成功必须成功"——闸门类工具最容易出的错是**该红的时候绿了**。

## 不做什么（Important Non-Goals）

1. **不做命令沙箱。** SignOff 不执行模型生成的命令，它执行的是仓库自己声明的命令（测试套件、收集脚本）。
   给这类命令套沙箱，等于假装能隔离"用户自己写的构建脚本"——隔离边界该由容器/CI 提供，不该由判定工具提供。
2. **不做 5 层纵深式的运行时防护。** 那一套的前提是"不可信输入会驱动真实机器操作"；
   SignOff 的不可信输入是提交内容与仓库配置，处理方式是**判定**与**留痕**，不是拦截执行。
3. **不证明"活是真人干的"。** 测试可以是假的；落印只证明"当时这套命令过了"。
4. **不防私钥泄露。** 锚点只能让重写历史变得可见。

## 外部审计就绪清单

审计买不买是预算问题，"能不能被审计"是工程问题。以下每项都要求"审计员能自己复现"，不是"我们声称"：

| # | 项目 | 状态 | 位置 |
| --- | --- | --- | --- |
| 1 | 威胁模型与信任边界 | 已写 | 本文件 |
| 2 | 攻击清单与对应测试 | 已写（A1–A7） | 本文件 + `test/selftest.js` |
| 3 | 负面用例：该红必须红 | 已有（178 处退出码断言） | `npm test` |
| 4 | 密钥/凭据处理 | 已写 | `lib/secrets.js`、`docs/gates.md` |
| 5 | 依赖面 | 运行时零依赖（仅 Node + git） | `package.json` |
| 6 | 架构自检（无环、基座不反向依赖、超限登记） | 已加 | `tools/arch-health.mjs` |
| 7 | 发布产物可复现（清单 vs 实际） | 已写 | `signoff release --pre/--post` |
| 8 | 漏洞披露与响应时限 | 已写 | `SECURITY.md` |
| 9 | **第三方审计报告** | **未做** | — |

第 9 项缺着，前 8 项的意义是：**审计员来了不用先花两周摸清边界**，而不是"我们已经安全"。
